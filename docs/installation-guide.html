Prerequisites

Three things, no more. Agent Embassy deliberately runs on nothing exotic — no Kubernetes, no cloud account, no managed database.

Before you start

All eight services — litellm, static, verify, keycloak, admin, openbao, agent (the privileged internal agent), stubs (its illustrative execution channels) — live in one docker-compose.yml with no Compose profiles. A single docker compose up starts all of them every time, and validates every required .env variable before anything starts — not just the ones the tier you care about needs. Fill in the whole .env file in the setup step below, even if you only plan to exercise Tier 0 today. Which tier's flows you exercise against the running stack is a choice you make with curl/the browser afterward — it isn't a choice you make by starting fewer containers.

One-time setup

~5 minutes, plus image pull/build time

Clone the repo, fill in real secrets, bring up the stack once, and generate local development certificates.

1

Copy the environment file and set real values

Nothing here has a working default — docker-compose.yml uses Compose's ${VAR:?error message} syntax for every credential, so a blank value fails fast with a clear message instead of silently running with admin/admin.

bash
# from the repo root
cp .env.example .env

Open .env and set: LITELLM_MASTER_KEY, ADMIN_UI_USERNAME, ADMIN_UI_PASSWORD, KEYCLOAK_ADMIN_USERNAME, KEYCLOAK_ADMIN_PASSWORD, ADMIN_INTERNAL_TOKEN, TIER3_INTROSPECTION_SECRET, and (since the internal-agent pivot) AGENT_INTERNAL_TOKEN and AGENT_STATUS_TOKEN — every one of these is validated up front, so docker compose up fails loudly if any is missing. AGENT_LLM_MODEL/ANTHROPIC_API_KEY are optional (the internal agent runs rules-only without them). Leave TIER2_AUDIENCE at its default (agent-embassy-tier2) unless you've also changed it in keycloak/realm-export.json and verify/keycloak_auth.py. See the configuration reference for what each one gates.

2

Bring up the stack

First run pulls litellm, nginx:alpine, keycloak and openbao and builds the verify and admin images from source — expect it to take a few minutes the first time. Keycloak's own health check can take up to two minutes before admin is allowed to start (it waits on keycloak: condition: service_healthy); the stack isn't stuck, Keycloak is genuinely still importing its realm.

bash
docker compose up
3

Generate local development certificates (for Tier 2)

Builds a throwaway CA, an nginx server certificate, and one example partner client certificate under certs/. Safe to run before or after step 2 — it only writes local files, which static's bind mount picks up live. The script refuses to overwrite an existing CA; delete certs/*.key certs/*.crt certs/*.srl first if you need to regenerate.

bash
./certs/generate-dev-certs.sh
Dev only

The CA's private key sits unencrypted right next to everything it signs. Never reuse these certificates outside local development.

System map

what docker compose up actually starts

Eight containers. Four — verify, openbao, agent and stubs — publish no port at all: they're reachable only from inside the Docker network, so a caller can't bypass nginx's certificate/token checks by forging a header straight to the backend.

litellm
:4000
MCP gateway fronting Tier 0/1 as tools (POST /mcp/); OTel traces to stdout. Tier 2/3 stay off it — mTLS caller-identity can't pass through a gateway.
static
:8080 · :8443
nginx serving the public catalog; gates Tier 1/2 resources via auth_request.
verify
internal only
Domain-challenge (Tier 1) + Keycloak JWT validation (Tier 2) + live introspection and mandate checks for Tier 3.
keycloak
:8082
OAuth2/OIDC token issuance for Tier 2 partner clients.
admin
:8090
Catalog CRUD, manifest editor, preview console, activity log, Tier 2 client management, Tier 1 config, Tier 3 approvals and internal-agent status.
openbao
internal only
Secrets store, mirrors Tier 2 partner credentials as a backup of Keycloak's own store — nothing reads from it yet.
agent
internal only
The privileged internal agent (Tier 3): routes an already-authorized handoff from verify to one execution channel, rules-first with an optional LLM step.
stubs
internal only
Illustrative mock ERP/Slack/email channels the internal agent executes against — no real ERP or messaging system is connected.

Tier 0 — Public catalog

no auth

An anonymous, unauthenticated catalog — the entry point every external agent starts from. Served directly by nginx, since LiteLLM has no built-in static-file serving.

1

Fetch the manifest

Every consuming agent is expected to discover the catalog by following this document's own links — never by hardcoding paths.

bash
curl http://localhost:8080/.well-known/agent-embassy.json
2

Fetch a catalog file

Placeholder example entries ship in static/ — replace them with real data before any real deployment.

bash
curl http://localhost:8080/catalog/products.json
3

Verify it end-to-end as two independent parties

tests/tier0_two_party.py plays the external-consumer role over real HTTP: it starts knowing only the base URL, discovers the catalog purely from the manifest's own links, validates the schema.org shape of each entry, and confirms contact.json (Tier 1) is refused without a session token.

bash
python3 tests/tier0_two_party.py            # defaults to http://localhost:8080

Tier 1 — Domain-verified contact routing

domain challenge

The same pattern ACME/Let's Encrypt uses to prove domain control before issuing a TLS certificate — proves control of a domain, not legal company identity (that's Tier 2). One resource is gated behind it: catalog/contact.json. All traffic below goes through nginx on :8080, which reverse-proxies verify's endpoints — verify itself has no port published to the host.

Verify

→

1

Request a challenge

bash
curl -X POST http://localhost:8080/tier1/challenge \
  -H 'Content-Type: application/json' -d '{"domain":"your-domain.example"}'
# => {"domain":"your-domain.example","token":"...","well_known_path":"/.well-known/agent-embassy-challenge.txt","expires_in":300}
2

Publish the token

As plain text at https://your-domain.example/.well-known/agent-embassy-challenge.txt, within 5 minutes (CHALLENGE_TTL_SECONDS).

3

Verify

bash
curl -X POST http://localhost:8080/tier1/verify \
  -H 'Content-Type: application/json' -d '{"domain":"your-domain.example"}'
# => {"session_token":"...","domain":"your-domain.example","expires_in":3600}
4

Use the session token

bash
curl http://localhost:8080/catalog/contact.json -H 'Authorization: Bearer <session_token>'
# without a valid token: 401, same as any Tier 1 resource
What this proves

Control of the domain at challenge time — comparable to single-vantage-point domain validation as it worked before the CA/Browser Forum required multi-perspective corroboration (2025). It does not prove legal company identity. Residual risks accepted rather than built around: no early session-token revocation before the 1-hour TTL, only partial subdomain-takeover mitigation, no multi-perspective validation. See ARCHITECTURE.md for the full reasoning.

✓

Run the service's own test suite

bash
cd verify && python3 -m venv .venv && .venv/bin/pip install -r requirements-dev.txt && .venv/bin/pytest

Tier 2 — OAuth2 + mTLS partner access

two independent proofs

Gates one example resource, catalog/order-status.json — an illustrative stub, since there is no real pilot supplier connector yet, the same posture as Tier 1's dropped PMS connector. Two proofs are required, checked by two different components:

OAuth2 access token

Issued by Keycloak via the client-credentials grant. Must carry aud=agent-embassy-tier2 — checked by verify/keycloak_auth.py against Keycloak's live JWKS.

+

mTLS client certificate

Presented on a dedicated TLS listener (:8443). Checked by nginx itself, before the request ever reaches the application layer.

Both required. A valid token over plain TLS is rejected; a valid client cert with no/expired token is rejected. Neither channel can compensate for the other.
1

Get an access token

Using the example partner client's credentials from keycloak/realm-export.json — change the secret before any real deployment.

bash
TOKEN=$(curl -s -X POST http://localhost:8082/realms/agent-embassy/protocol/openid-connect/token \
  -d 'grant_type=client_credentials' -d 'client_id=example-partner' \
  -d 'client_secret=example-partner-dev-secret-changeme' | python3 -c 'import sys,json;print(json.load(sys.stdin)["access_token"])')
2

Call the Tier 2 resource over mTLS

Presenting the example client certificate generated in setup, plus the token.

bash
curl --cacert certs/ca.crt --cert certs/client-example-partner.crt --key certs/client-example-partner.key \
  -H "Authorization: Bearer $TOKEN" https://localhost:8443/catalog/order-status.json
# missing/wrong cert: TLS-level 400 (nginx never reaches the app layer)
# valid cert but missing/invalid/expired token: 401
What this proves

The caller holds a Keycloak-issued token scoped to this service and controls the private key for a certificate nginx's TLS listener accepted — two independent channels, not one mechanism wearing two names. TLS session resumption is disabled on this listener (ssl_session_tickets off; ssl_session_cache off;) — without it, nginx skips re-verifying the client certificate on a resumed session. Residual risk accepted rather than built around: no token revocation before its 5-minute TTL expires (Keycloak default).

✓

Run the service's own test suite

Now includes Tier 2 cases — a real RSA-signed JWT is verified against a stubbed JWKS fetch, keeping the actual signature/claims-verification code path real; only the network fetch of Keycloak's public keys is mocked.

bash
cd verify && .venv/bin/pytest

Tier 3 — Mandates, approval queue, internal agent

stub channels

A feasibility demo against illustrative stub channels — no real PMS/ERP or messaging system is connected, the same posture Tier 2's order-status.json already takes, and deliberately so: no partner will let Tier 3 touch their real system before seeing it proven against something fake first. Uses an illustrative example throughout: a laundry supplier auto-reordering up to €400/week.

Tier 3 does not connect directly to a PMS/ERP: verify (the gateway) authenticates, checks the mandate, reserves budget, and hands a fixed-schema envelope to the privileged internal agent — a separate agent/ container, part of the product but swappable by each company — which routes the action to an execution channel (a mock-ERP order endpoint, a Slack-shaped webhook, an email-shaped send, all in stubs/, none published to the host) and reports back.

Grant a mandate
a weekly limit, set by a human
→
02
Place an order
within limit: executes now
→
03
Beyond the limit
queued for human approval
→
04
Revoke
takes effect immediately
1

Grant a weekly limit

On a partner's page under Partner clients, set a "Tier 3 — deep integration" weekly limit, in whole euros. This is the "explicit human approval" step. Like Tier 1's config, the grant is hot, not persisted — it lives in verify's process memory and reverts on a restart.

2

Place a mock order

As that partner, over the mTLS :8443 listener (same certificate/token setup as Tier 2).

bash
curl --cacert certs/ca.crt --cert certs/client-example-partner.crt --key certs/client-example-partner.key \
  -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"item": "Bath towels (24-pack)", "quantity": 1, "amount_cents": 5000}' \
  https://localhost:8443/tier3/orders
# within the mandate: 201, a schema.org Order executed by the internal agent
#   (orderNumber is the stub channel's reference; the body names the channel
#   and an action_id you can poll at GET /tier3/orders/<action_id>)
# beyond the mandate's remaining budget: 202 pending_approval — queued for a
#   human decision, NOT rejected, and does not consume budget
# no grant for this client at all: 403
# revoked/disabled/expired token: 401
# internal agent container down: 503, fail closed, budget not consumed
3

Approve or reject a queued order

An order beyond the mandate waits on the admin UI's Approvals page (http://localhost:8090/approvals) until a human approves it (executes it, counts it against the mandate) or rejects it — or it expires on its own. The queue is bounded per client and, like everything else in verify's store, in-memory: a restart clears it.

4

Revoke access immediately

Click "Disable" on the partner's page (same page as step 1). The very next /tier3/orders request with that partner's still-unexpired token now gets 401, while the SAME token still gets 200 from Tier 2's order-status.json — concrete, live proof that Tier 3's revocation is real and Tier 2's isn't (by design — see the callout below). Revoking the Tier 3 grant itself also cancels that client's still-pending approvals.

5

Review the audit trail

At http://localhost:8090/tier3-audit — every attempt (accepted, rejected, queued, expired) with its reason and action_id.

What this proves

Tier 2's /tier2/check validates JWTs locally against Keycloak's published JWKS — disabling a Keycloak client does not invalidate tokens it already issued; they stay valid until their own 5-minute TTL expires. Tier 3 instead calls Keycloak's real token-introspection endpoint (RFC 7662) on every request — a disabled client fails introspection immediately. This is a genuine, live-verified architectural difference, not a claim: the same still-unexpired token gets 401 from Tier 3 and 200 from Tier 2 at the same moment (step 4 above).

The internal agent's routing is rules-first

agent/rules.json is the operator-edited routing table (first match wins; edit it and restart the agent container). A rule can name a channel directly, or delegate to "llm" — only then is a model consulted (optional; leave AGENT_LLM_MODEL/ANTHROPIC_API_KEY unset and the agent runs rules-only). The LLM's entire authority is picking one channel from the rule file's own allowlist; its output is validated by exact string equality, and anything unusable means the action fails — never a guessed default channel. The worst a prompt injection via an order's item text can achieve is a different pre-authorized channel for an already-authorized, budget-checked action. Three separate secrets gate the three edges (verify→agent, admin→agent status, admin→verify) — the agent, the one component that ingests attacker-influenced text, holds no token verify itself accepts.

Admin UI

port 8090

A server-rendered web UI for a pilot client's own admin to manage their public Tier 0 catalog and manifest without editing JSON by hand.

1

Log in

Open http://localhost:8090 and sign in with ADMIN_UI_USERNAME/ADMIN_UI_PASSWORD from your .env — HTTP Basic Auth, a single shared credential, the same pattern as LITELLM_MASTER_KEY.

Out of scope, on purpose

Tier 1 config (TTLs, rate limits) is editable live from the admin UI's "Tier 1 config" page — verify applies a change immediately, no restart needed. It is a hot-reload, not a persist: the change lives only in verify's process memory and reverts to the env var default in docker-compose.yml/.env on the next restart. Tier 2's certs/contact.json/order-status.json are not editable here — those stay JSON/CLI-managed. Catalog and manifest writes go straight to the files nginx serves — no restart needed — and are atomic (temp file + os.replace), so nginx never sees a half-written file.

Managing Tier 2 partner clients

/keycloak-clients

Manages Tier 2 partner OAuth clients through Keycloak's real Admin REST API — no new identity system. It replaces hand-editing keycloak/realm-export.json for day-to-day partner onboarding (that file still governs the realm itself, the example-partner client, and certs).

Why this exists

A client added by hand that forgets the oidc-audience-mapper protocol mapper (the one that sets aud=agent-embassy-tier2) fails Tier 2 auth silently — collapsed into the same generic "invalid token" as every other failure. Every client this page creates gets that mapper attached automatically, byte-for-byte the same shape as example-partner's.

1

Add a partner client

At http://localhost:8090/keycloak-clients, pick a client ID (this becomes the partner's OAuth client_id) and a name.

2

Reveal the secret

On the new client's page. Keycloak generates it; this page can only show it via a dedicated POST — never a GET — so it never ends up in a URL, browser history, or Referer header. It can be revealed again any time; regenerating it invalidates the old one immediately.

3

Hand the partner their credentials

They authenticate exactly as shown in Tier 2's curl example above, with their own client_id/secret in place of example-partner.

Credential note

This page talks to Keycloak using KEYCLOAK_ADMIN_USERNAME/KEYCLOAK_ADMIN_PASSWORD — Keycloak's own bootstrap realm-admin account. Treat it accordingly; it's full realm-admin access, not scoped to client management.

✓

Run the test suite, and the strongest available end-to-end check

Creates a partner client through the admin UI, reveals its secret, mints a real access token from Keycloak with it, then runs that token through the actual verify/keycloak_auth.validate_access_token() inside the already-running verify container — not a reimplementation of that check — before deleting the client.

bash
cd admin && .venv/bin/pytest
bash
ADMIN_UI_PASSWORD=<value from your .env> python3 tests/tier2_admin_smoke.py

Troubleshooting

Real issues you may hit, and why they happen.

!

"set LITELLM_MASTER_KEY in .env" (or any other :? variable) on docker compose up

Expected and by design — Compose validates every required variable across all eight services before starting anything. Fill in the whole .env file, not just the tier you're working on.

!

admin doesn't start for up to two minutes

admin waits on keycloak: condition: service_healthy. Keycloak has no curl/wget in its image, so its health check is a TCP connect probe with up to 60 retries at a 2-second interval — it genuinely takes that long to import the realm and finish booting on a cold start. Watch progress with docker compose logs -f keycloak.

!

Tier 2 curl fails with a TLS/certificate error

Run ./certs/generate-dev-certs.sh from the repo root if you haven't yet — Tier 2's mTLS listener has nothing to verify against until it has. The script is idempotent by refusal: if certs/ca.key already exists it exits without regenerating; delete certs/*.key certs/*.crt certs/*.srl first if you actually need fresh ones.

!

Browsers warn about the Tier 2 certificate

Expected — certs/ca.crt is a throwaway local development CA, not trusted by any real certificate store. Use curl --cacert certs/ca.crt ... (as shown above) rather than importing the dev CA anywhere persistent.

!

Tier 0's activity page is empty but docker compose logs static shows requests

Different log paths on purpose: the admin UI reads ./static-logs/access.log on the host (bind-mounted over nginx's /var/log/nginx so a second container can read it), which means those lines stop showing up in docker compose logs static — they're not lost, just relocated.

!

A token or session stopped working after a while

By design, not a bug: Tier 1 challenge tokens expire after 5 minutes, Tier 1 session tokens after 1 hour, and Tier 2 access tokens after Keycloak's default 5 minutes — none of them can be revoked early before that TTL runs out. Request a fresh one.

!

Port already in use

4000, 8080, 8443, 8082, or 8090 may already be bound by something else on your machine. Edit the host side of the relevant ports: mapping in docker-compose.yml — the container-side port stays the same.
